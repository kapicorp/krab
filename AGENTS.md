# AGENTS.md

Instructions for coding agents working in this repository. `CLAUDE.md` imports
this file, so there is one copy to maintain.

## What this is

`krab` is Kapitan rewritten in Rust. It reads the same `.kapitan`,
`inventory/classes`, `inventory/targets`, `refs/` and `resolvers.py` as the
Python implementation, and `docs/ARCHITECTURE.md` says what the crates do.

Output must be byte-identical to kapitan 0.36.3 with the omegaconf inventory
backend. Merging, interpolation, resolvers, YAML and JSON emission and compiled
output are ports of Python behaviour rather than fresh implementations of the
same idea. The deliberate differences are listed in `docs/DECISIONS.md`, and a
new one needs a row there before it merges.

## Commands

```sh
cargo build --release                      # target/release/krab
cargo fmt --all --check
cargo clippy --all-targets --locked
cargo test --locked
cargo test -p krab-inventory --test fixture               # one test binary
cargo test -p krab-inventory renders_like_the_reference   # one case, by its name
```

Tests that need more than cargo:

* The Python resolver tests (`crates/krab-inventory/tests/python_resolvers.rs`)
  and the kadet tests (`crates/krab-compile/tests/kadet_runner.rs`,
  `crates/krab/tests/kadet_isolation.rs`) need a `python3` with the packages
  CONTRIBUTING.md names, `crates/krab/tests/helm_input.rs` a `helm` binary.
  Without them they pass without running. The reason is printed on stderr,
  which cargo shows only with `cargo test -- --nocapture`. With `CI` set they
  fail instead (helm only on Linux).
* The corpus test (`crates/krab-inventory/tests/corpus.rs`) runs only when
  `KRAB_CORPUS` and `KRAB_COMPILED` point at a real inventory and reference
  output.
* `tests/fixtures/expected/*.yaml` is generated by the Python kapitan, not by
  krab (`tests/fixtures/README.md`). Every engine behaviour change gets a
  fixture case plus regenerated expected output.
* LSP without an editor: `python3 scripts/lsp-smoke.py <repo> <file> 1:10` and
  `scripts/lsp-smoke-live.py <repo>` (both need `krab` on `PATH`).
* VS Code extension: `cd editors/vscode && npm ci && npm run package`.

After touching loading, merging, interpolation, resolvers, emitters or
compile, run the parity check against a real inventory. CONTRIBUTING.md has the
commands.

Rebuilding does not require stopping anything: each build hashes into its own
daemon socket, so a dev build and the installed release coexist.

## Architecture

`docs/ARCHITECTURE.md` is the guided tour: the crate layering, a code map per
crate, the four cross-cutting invariants (provenance, Python-compatible
equality and stringification, `Diagnostic` errors, daemon/local parity), and
an Extending section listing every place a new resolver, input type, RPC
method, `.kapitan` key and the like touches. Read it before changing anything
across crate boundaries.

`docs/specs/` states what each area must do, with requirement IDs and open
deviations; a change edits the spec it touches. `docs/exec-plans/` holds
plans for larger changes.

## Conventions

* Commit messages: `area: what changed` (`lsp: accept the --stdio flag`).
* `docs/CLI.md` is the flag reference and must stay in sync with `--help`;
  `docs/DESIGN.md` carries the semantics.
* Open work is tracked on the GitHub project board linked from `docs/ROADMAP.md`,
  not in the repo.
* Contributors work from a fork and cannot merge. Nothing should be planned
  whose next step is a merge landing: if a change needs another one first, say
  so in the pull request and keep it reviewable on its own.
* Splitting work into pull requests goes by dependency, not by file. Before
  opening two that touch the same file, merge both branches onto a scratch
  branch off `main` and build it: a conflict can first appear only once a
  third branch lands, so checking them in pairs is not enough.
* A version number in prose survives only where a test compares it to its
  source. Anywhere else, derive it or leave it out.
* Work that is deferred or rejected goes on the tracking issue with its
  reason. A decision kept in a conversation is gone by the next one.
* Releasing is a maintainer's job, and the rest of this list still applies to
  the pull request that prepares it: bump `version` in the workspace
  `Cargo.toml`, and `editors/vscode/package.json` when it changed. The tag
  comes after the merge and `release.yml` refuses one that disagrees with the
  manifest. CONTRIBUTING.md has the command.

## Environment variables

`KRAB_INVENTORY_PATH`, `KRAB_NO_DAEMON`, `KRAB_PYTHON` (interpreter for
resolvers and kadet), `KRAB_PYTHON_REQUIREMENTS`, `KRAB_CORPUS` / `KRAB_COMPILED`
(corpus test only).

## Operating krab

`.claude/skills/krab/SKILL.md` covers *using* the binary against an inventory
(daemon model, inspection commands, parity workflow). Read it before driving
`krab` on a real repository rather than rediscovering the CLI.
